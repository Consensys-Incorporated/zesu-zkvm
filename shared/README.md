# shared

zkVM-independent crypto for the zesu guest builds: the pure-Zig implementations that more than one
target needs, and their unit tests. The point is to write (and test) each algorithm once, instead
of once per zkVM.

Nothing here knows about any zkVM's ISA, syscalls or I/O. A target imports one module,
[`src/zkvm_crypto.zig`](src/zkvm_crypto.zig), from its own `build.zig`:

```zig
const crypto_mod = b.createModule(.{ .root_source_file = b.path("../shared/src/zkvm_crypto.zig"), ... });
accel_impl_mod.addImport("zkvm_crypto", crypto_mod);
```

(It has to be one module: Zig does not allow a file to belong to two modules, and these files
import each other.)

## What is here

**Standalone primitives**: complete implementations with no backend to plug in. A target with no
accelerator for them just calls these.

| File | Implements |
|---|---|
| `ripemd160.zig` | RIPEMD-160 (precompile 0x03) |
| `blake2f.zig` | BLAKE2b F compression (EIP-152, precompile 0x09) |
| `modexp.zig` | big-integer modular exponentiation (EIP-198, precompile 0x05) |
| `bls12_381_map_constants.zig` | isogeny / cofactor constants for MAP_FP_TO_G1 / MAP_FP2_TO_G2; generated by `scripts/gen_bls12_381_map_constants.py` from `py_ecc` |

**Curve code generic over a field backend**: the algorithms (curve arithmetic, pairing, ECDSA,
map-to-curve, KZG) written against a small backend interface, so the same code runs natively under
`zig test` and in a guest on that zkVM's accelerated field/point operations.

| File | Implements |
|---|---|
| `soft.zig` | the software field backend (the interface contract is documented at its top); used for native tests |
| `field.zig` | prime-field arithmetic over a backend |
| `tower.zig` | Fp2 / Fp6 / Fp12 extension tower (BN254 and BLS12-381) |
| `secp.zig` | secp256k1 / secp256r1 ECDSA verify, secp256k1 recovery; `ecdsa_soft.zig` is the `std.crypto` reference it is tested against |
| `bn254.zig` | BN254 G1 add / mul and optimal-ate pairing (EIP-196/197) |
| `bls12_381.zig` | BLS12-381 G1/G2 add and MSM, pairing, map-to-curve (EIP-2537), KZG point evaluation (EIP-4844) |

The `*_vectors.zig` files are test data (EIP vectors, c-kzg-4844 KZG cases). They are used by the
native tests and by the in-VM self-tests of targets that have them.

## Using the generic code from a target

A target supplies a backend with its own accelerators and instantiates the generic code with it.
`pico/src/zkvm_accel/{secp,bn254,bls12_381}.zig` are the worked example: each is a thin file that
defines Pico's backend (`pico_fp.zig` field ops, the curve-point syscalls) and exposes the guest
API, with `Impl(PicoBackend)` doing the work. Anything specific to a zkVM stays in the target:
syscall wrappers, backends, the guest self-test that runs on the VM. Anything that is just
mathematics, and any test that can run natively, belongs here.

What is *not* shared (yet): OpenVM's `bn254.zig`, `bls12_381.zig`, `secp256k1.zig` and
`secp256r1.zig` are written directly against OpenVM's intrinsics, not against the backend
interface, so they still live in `openvm/`. Porting them to instantiate the code here would remove
the duplication; it needs OpenVM-side backends for the field and point operations.

## Tests

```sh
cd shared && zig build test                      # all native unit tests (about 2 min in Debug)
cd shared && zig build test -Doptimize=ReleaseFast
make -C pico unit                                # the same, from pico/
```

Tests include the official EIP-196/197/2537 vectors, the Besu EIP-2537 CSV suites, the c-kzg-4844
`verify_kzg_proof` vectors, ECDSA differential tests against `std.crypto`, and property tests
(bilinearity, subgroup orders, Frobenius). The Besu CSVs are not copied into this repo: they come
from the zesu dependency pinned in `build.zig.zon` (keep that pin in step with
`pico/build.zig.zon`).

## Adding to this directory

- Keep it free of zkVM-specific imports (`pico_sys` and the like); that is what makes it shareable.
- New files go in `src/` (flat, so they can import each other by relative path) and are exported
  from `src/zkvm_crypto.zig`; add any file with tests to `test_roots` in `build.zig`.
- Name the specification or reference an implementation follows in its header, as the existing
  files do (see the provenance table in [`pico/README.md`](../pico/README.md)).
